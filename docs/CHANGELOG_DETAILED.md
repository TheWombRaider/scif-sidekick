# Detailed changelog

The full release notes, with the reasoning behind each change. The short version is [CHANGELOG.md](../CHANGELOG.md).

## 1.29.0
- **Second mail provider: Microsoft Graph (Outlook.com).** `GraphGateway` implements `MailTransport` and passes the same `MailTransportContract` as Gmail, run against `FakeGraphServer`, an in-memory simulation of the Graph subset the app uses. Nothing has been checked against a real Microsoft account yet; the first real checks, and every Graph assumption the code makes, are listed in `docs/TEST_PLAN.md` §18.
- **Device code sign-in, no MSAL.** MSAL would bring several libraries and a redirect URI bound to the APK's signing key. The device code flow needs two HTTPS endpoints the app can call with the OkHttp it already has, no redirect, and works when the phone is the awkward device to type on: the code can be entered anywhere. No Gradle dependency was added. The client ID is the owner's own free Entra registration and is public.
- **One stored refresh token, encrypted.** Microsoft has no on-device broker like Google Play services, so the app stores one refresh token, AES-256-GCM under a non-exportable Android Keystore key (`scif_ms_refresh_v1`), never in the settings export. Disconnect deletes the token and the key. Access tokens stay in memory. The threat model is in `docs/DESIGN_NOTES.md`.
- **`MailRouter` rules.** The preferred account is tried first. An authorization failure or a definite failure (an error response other than 5xx, or no connection at all) moves to the other account. An ambiguous failure (timeout, reset, 5xx) checks that account's Sent folder first; if the message isn't found or the check can't run, the other account sends and the event log says "possible duplicate". A rare duplicate is better than a lost forward. Retries after a crash check every account's Sent folder before sending. Both inboxes are polled and command candidates are interleaved, preferred first, so one inbox full of junk can't push the other out of the 20-message window. With only Gmail set up the router is a pass-through, so Gmail-only installs make the same calls as in 1.28.1 (the stricter sender check and an alert that is no longer re-posted while already showing are the visible differences).
- **A Gmail removed on purpose stays removed.** With Outlook set up, disconnecting Gmail sets a flag that takes it out of the router, so it isn't alerted or reported as needing reconnection, and forwarding stays on if Outlook is connected.
- **Per-provider reconnect alerts.** `AuthAlertCoordinator` is now the single owner of the "Reconnect Gmail" / "Reconnect Outlook" notifications: raised on an auth failure or at service start, cleared on the next success, and checked every 30 seconds only to clear stale ones. The first draft gave Outlook's alert the id 4104, which is already the delivery-review notification, so clearing a reconnect alert would have silently cancelled a "Delivery needs review" warning. Outlook now uses 4110 (any other provider 4111), Gmail keeps 4103, and `NotificationIdsTest` fails if any two notification ids collide.
- **Sender authentication, both providers, fail closed.** `GraphAuthentication` reads only the first `Authentication-Results` header and needs exactly one dmarc clause, `pass`, with its own `header.from` equal to the `From` domain. Comments and quoted strings are stripped first (a draft parser accepted a `dmarc=pass` hidden in a quoted reason after a `;`), and because stripping could let a forged `(` swallow a real `dmarc=fail`, a raw second mention of "dmarc" rejects the header. `GmailAuthentication` was hardened to the same rules, with one exception for the dmarc result Gmail reports inside its ARC comment, so ARC-sealed mail (for example from Microsoft 365 senders) still authenticates. Domains and addresses must be ASCII before lowercasing.
- **Attachment budget.** Graph refuses requests over about 4 MB, and a MIME draft is base64-encoded twice (about 1.83 times the source size), so Outlook forwards carry at most 1,912,568 bytes of attachments in total. Over that, all attachments are left out with the "Attachment not forwarded" note, which now names Outlook. Gmail's 18 MB budget and its exact output are unchanged.
- **Polling.** Graph has no push the phone can receive, so Outlook is polled on the 30-second reply tick: a 90-day sweep first and every 6 hours, otherwise from 10 minutes before the newest message seen (server time). A poll that couldn't read its whole window keeps its cursor and sweeps again soon.
- **UI.** Settings → Email accounts has a Microsoft (Outlook.com) card (client ID, Connect, the code panel with Copy code and Open page, Send first, Disconnect), and Home shows an Outlook chip once an account exists. The sign-in code is never logged, and Open page only opens https Microsoft addresses.

## 1.28.1

Email caps are unchanged because they sit just under Gmail's own daily sending limit.

## 1.26.0
- **Owner address gets all four commands** on first Gmail connect (Compose, Enable, Disable, Status), seeded once per install. Installs that already seeded a Status-only owner are not changed.
- **Commands screen** in the menu, built from one `CommandHelp` table that unit tests check against the real subject parser.

## 1.25.0

- **Widget toggle moved out of the exported receiver.** `StatusWidgetProvider` has to be exported (the launcher delivers updates to it), and its on/off action could therefore be sent by any app. The action now lives in `WidgetToggleReceiver`, which is not exported; a unit test parses the manifest and fails if the exported set changes.
- **Remote-command search can't be starved.** `RemoteEnableWorker` used to look at only the newest unread tagged message, so junk could hide a real `[SCIF:ON]` until it aged out of the 2-day window. It now searches only the allowlisted senders and examines up to 20 messages per run via `RemoteCommandPlanner`: unauthorized or ambiguous ones are marked read, the first authorized enable wins. Consequence: a stranger's `[SCIF:ON]` is no longer logged by the worker path, since it is never fetched; the service path still logs such attempts.
- **Receipts are durable.** `RemoteCommandReceipt` queues the email and enqueues `ReceiptDrainWorker` (WorkManager, network constraint, bounded retries) instead of draining inside the reply poll, which the service cancelled when it stopped itself after `[SCIF:OFF]`. Startup recovery now releases only email rows with no delivery attempt in the last three minutes, so it can't grab a send another component is making. The ON receipt reports when the forwarding service could not be started.
- **SMS and system-mail limits.** SMS: 10/minute, 60/hour, 200/day (hard). Ordinary forwards stop at 20/290/420 so receipts, status replies and the heartbeat keep a reserve inside the existing 20/300/450 email totals. `PremiumNumbers` blocks well-known premium-rate and satellite prefixes at reply time and again in the SMS/MMS gateways; it is a safety net, not a complete list.
- **Owner address is Status-only** on first Gmail connect and is seeded once per install, so removing it sticks. Compose, Enable and Disable are granted in Settings.
- **Blocked-attempt logging is capped** at 20 per hour, followed by a single summary row.
- **Backups:** PBKDF2 iterations raised to 600,000, recorded in the file as `iter`; backups without it restore with the old 210,000. An absurd `iter` is refused. The export screen warns when no passphrase is set.
- **Hide app content in Recents** (Settings): `FLAG_SECURE`, off by default, stored in SharedPreferences.
- **Accessibility first pass:** switch and checkbox rows are merged so they are read with their label; filter-card controls have descriptions.
- **Build and CI:** Gradle wrapper replaced with the official jar (checksum matches services.gradle.org) and moved to Gradle 9.8.0; AndroidX, Room, WorkManager and coroutines updated; optional release signing from a gitignored `keystore.properties`; CI validates the wrapper, runs lint and the history-query safety check, adds dependency review and CodeQL, with actions pinned by SHA.
- **Docs:** README disclaimer, anchors fixed, install/troubleshooting/limits sections; stale README references in code comments now point at `docs/DESIGN_NOTES.md`; ARCHITECTURE's reply-poll description corrected.

## 1.24.0

- **Email confirmation for `[SCIF:ON]` and `[SCIF:OFF]`.** An authorized remote command now gets a reply: "Forwarding ENABLED" or "Forwarding DISABLED", with the status summary read back after the change, so the receipt reflects what actually happened. Rejected or unauthorized commands still get no reply, so a stranger can't use the app to confirm the mailbox is live, and a forged From can't turn the reply into backscatter. The receipt is drained immediately, because the forwarding service stops itself after an OFF and would otherwise never send it.
- **README rewritten** around features and usage tables. The previous long-form text moved to `docs/DESIGN_NOTES.md`.

## 1.23.1

- **Custom heartbeat interval.** Settings → Heartbeat email → "Send every" now has a "Custom hours (1-720)" field next to the 6h/12h/24h/48h presets. Both write the same `heartbeatIntervalHours` value -- tapping a preset updates the field, typing a number deselects the presets. The worker already tolerated any positive hour count; only the UI was limited to four fixed choices.

## 1.23.0

- **Remote control by email consolidated into one place.** Compose a new text, Enable forwarding, Disable forwarding, and Ask for status used to be four separate toggles, each with its own allowlist you had to type the same address into repeatedly. They're now one "Remote control by email" card: a single master switch (one-tap kill switch for all four) plus one address list, where each address gets its own independent checkbox per command -- trusting an address for one command still never implies trusting it for another.
- **On by default.** This app is built for personal, single-owner use, where a feature that has to be discovered and switched on separately per command adds friction without adding real safety. The master switch defaults on, and the Gmail account you connect is authorized automatically the first time, with every capability checked, so the feature does something out of the box instead of sitting on but empty. A newly added address also starts with everything checked.
- Upgrading installs keep exactly what they already had: an address already authorized under one of the four old lists, with that list's own toggle on, keeps precisely the capability bit(s) it already had -- nothing is added, only consolidated. See `Database.MIGRATION_17_18`.
- Backups made under the old format still restore correctly, merged into the new model the same way.

## 1.22.0

- **Faster forwarding.** A newly arrived SMS, MMS or RCS message now wakes the forwarding loop immediately instead of waiting out its 10-second tick, and a short, bounded wakelock (at most 60 seconds) keeps a screen-off phone awake from arrival until that forward's send pass has run. Previously nothing held the CPU up, so an idle phone could sleep between receiving a text and emailing it. Each successful forward's History entry now says how long after arrival it was sent.
- **Cheaper, faster reply polling.** The Gmail reply poll now asks Gmail's history log whether the inbox changed (one small request) and only searches when it did, instead of paging through every matching message each time. A full sweep still runs at startup, when the history cursor expires, and every 6 hours. That made a shorter interval affordable: replies and `[SCIF:...]` commands are now picked up about every 30 seconds instead of 90.
- **Tighter reply authorization.** Replying from an address on the "Compose a new text from email" allowlist (rather than the filter's own recipient) now works only while that feature is switched on, and every such acceptance is logged as a security event.
- **Least-privilege Google access.** The Cloud Pub/Sub scope is requested only while Gmail push (beta) is on; a missing Pub/Sub grant can no longer interrupt ordinary forwarding. Settings offers "Grant push access" when push needs it.
- **RCS self-echo guard.** A messaging-app notification whose newest line is the user's own sent message is ignored rather than forwarded as if the contact had sent it.
- **Watchdog** restarts a dead forwarding service after 10 minutes without a heartbeat instead of 20.
- **CI** (GitHub Actions) runs the history-query safety check, unit tests, lint, and a debug build on every push.

## Earlier releases

This working build is release **1.21.0**. Release 1.21.0 adds **outbound SIM selection** (Settings → "Send texts from"), closing the dual-SIM follow-up that `IMPLEMENTATION_PLAN.md` §3 deferred back at 1.4.0 for want of a second SIM to verify against. Both gateways already resolved `SubscriptionManager.getDefaultSmsSubscriptionId()`, so dual-SIM devices worked — as long as the system default happened to be the line you wanted, with no way to say otherwise.

The design is built around not turning a working send path into a broken one. The default, `SYSTEM_DEFAULT`, reproduces the old behavior exactly, so an install that never touches this setting is on precisely the code path that shipped before it, and migration 16→17 defaults every upgrading install there. A specific SIM is honored **only when it can be positively confirmed active at send time** — a pulled SIM, a deleted eSIM profile, an id restored from a different handset, `READ_PHONE_STATE` not granted, or the platform call throwing all fall back to the system default rather than attempting a send on a subscription that may not exist. The check is deliberately written as "confirm, or fall back" rather than "try it and see", so the failure modes degrade to *behaves like it did before*, never to a failed text.

It is also invisible unless it applies: the card renders only when the device genuinely has more than one SIM slot, which is checked via `TelephonyManager` without any permission at all. On a single-SIM phone the setting does not exist. `READ_PHONE_STATE` is requested lazily, only if the picker is actually opened, and declining it is a supported outcome rather than an error. The chosen id is excluded from backup/restore on purpose — a subscription id means something only on the handset that issued it.

Release 1.20.0 adds **`[SCIF:STATUS]`** (Settings → "Ask for status by email"), the read-only third command: email it and get back the same summary the heartbeat sends. Unlike the two master-switch commands it is meaningful in *either* state, so it is the one command both sides check — `ForwardingService`'s reply poll answers it while forwarding is on (~90s), `RemoteEnableWorker` while it is off (~15min) — and since those two are never alive at once, whichever can see the mail is the one that handles it. The authorization check, reply body, and mark-as-read handling live in a single shared responder specifically so those two paths can't drift into answering the same question by different rules. It gets its own toggle and allowlist rather than riding on the enable or disable pair: it changes nothing, but it does disclose operational state, and being trusted to switch forwarding on is not the same as being trusted to ask what it's doing. The reply carries no message content, phone numbers, or sender addresses.

Release 1.19.1 fixes a bug in 1.19.0 found immediately after merging it: the heartbeat was queued but never actually sent while forwarding was switched off — which is one of the two states it most needs to be able to report. `ForwardingService` is the only thing that drains `send_queue`, and its loop calls `stopSelf()` on finding the master switch off *before* reaching its drain calls, so the row sat there until forwarding came back on, i.e. exactly until it no longer mattered. The worker now drains the email channel itself after queuing; doing that concurrently with the service is safe, because claiming a row goes through the same single-winner `queueDao().claim()` guard either way.

Release 1.19.0 adds an opt-in **heartbeat email** (Settings → "Heartbeat email"): a short status summary on a fixed cadence — forwarding on or off, whether the service is alive, Gmail authorization, queue depth, send attempts in the last 24 hours. The point of it is the message that *doesn't* arrive. Every other way this app reports trouble — the circuit breaker opening, Gmail needing reauthorization, a delivery needing review — is an on-device notification, which is precisely useless in the situation the app is built for: the phone is somewhere you are not. And the failure that matters most is silent by construction, since a Testing-mode OAuth grant expires on a schedule and, when it does, no error email can be sent to tell you — sending email is the part that broke. A heartbeat inverts that: absence becomes the signal. It deliberately keeps running when forwarding is off (that state is itself worth learning from a distance, and a heartbeat that went quiet whenever the master switch flipped would be indistinguishable from the app dying), it is not gated on Gmail being authorized (the mail simply waits in the queue and goes out when authorization returns), and it carries no message content, phone numbers, or sender addresses — it is a status report, not a way to read the message history out of the phone.

Release 1.18.0 closes a blind spot the email-reply path has had since it existed: replying to a forwarded email either became a text or didn't, and the sender had no way to find out which. The outcome was recorded in `event_log`, in the in-app History, and -- only after five failed attempts -- in an on-device notification, every one of which needs the phone that this whole path exists to work without. Now, when an email-initiated text reaches a terminal state, SCIF Sidekick emails the sender back: delivered, or failed with the reason and an explicit "nothing was sent." On by default, and it is the one opt-in here that defaults on, because unlike every other toggle in this area it authorizes nothing -- it only reports an outcome back to someone who already proved they were allowed to cause it. A failure is reported once the send has genuinely given up, not on each retry, and the confirmation is queued through the same `send_queue` as everything else rather than sent directly, so it inherits the rolling caps, the circuit breaker, the retry backoff, and durability across process death instead of carving an exception into any of them. It confirms the phone handed the text to the network; it is not a read receipt, and carrier delivery to the recipient's handset is not something this app can observe.

Release 1.17.0 adds the counterpart to 1.16.0: an opt-in "[SCIF:OFF]" command email that turns the master forwarding switch back *off*. It is checked in a different place than the "on" command, for the same reason that one needed its own worker — whichever component is actually alive in the state the command is about is the one that can see it. Forwarding being on means `ForwardingService` is running and already polling this inbox every 90 seconds, and already consumes any unrecognized `[SCIF:` subject (marking it read and recording it as an ignored candidate); a 15-minute worker looking for one still unread would therefore almost never find it. Handling it inline in that poll is both the only reliable place and the faster one — about 90 seconds rather than 15 minutes. It has its own toggle and its own allowlist, deliberately not shared with the "on" pair: the two fail in opposite directions, and authorizing someone to start forwarding must never implicitly authorize them to stop it. See [Remote control by email](DESIGN_NOTES.md#remote-control-by-email).

Release 1.16.1 is a battery fix in the RCS notification listener. `onNotificationPosted` fires for every notification from every app on the device -- that is the only way `NotificationListenerService` works at all -- and for each one that wasn't from Messages, the default-dialer check made a fresh `TelecomManager` binder call to `system_server` just to decide to ignore it: the same "binder call on every tick, all day" shape diagnosed in 1.13.2, per-notification instead of per-timer-tick. The default dialer essentially never changes while the listener stays connected, so it is now read once in `onListenerConnected` and cached, with a lazy one-shot retry if that first read returns null. Prompted by a report of battery use even with forwarding off; this is a real, disclosed inefficiency, not a confirmed root cause -- no on-device profiling was available to verify it against the reported symptom.

Release 1.16.0 adds "Enable forwarding by email" (Settings → Behavior): an opt-in "[SCIF:ON]" command email that turns the master forwarding switch back on even while it's off and the app itself isn't running to notice anything -- for the moment forwarding was left off and the phone is out of reach (locked away outside a SCIF, say). This needed its own always-scheduled 15-minute background check independent of `ForwardingService`, since that service only runs -- and only polls Gmail at all -- while forwarding is already on; see `RemoteEnableWorker`'s doc comment. Backup/restore covers the new toggle and its allowlist, on the same terms as the compose-new allowlist: a restored backup can only turn the feature *on* if that backup also carried the allowlist it should be gated by. See [Remote control by email](DESIGN_NOTES.md#remote-control-by-email).

Release 1.15.0 added an **About** screen (hamburger menu): an app-identity card, developer info, and a changelog, the latter hand-maintained in `Changelog.entries` — the same idea as the pre-1.9 releases' throwaway `INSTALL.txt` "WHAT'S NEW" sections, given a permanent in-app home. It was backfilled from the four surviving `INSTALL.txt` files (1.1.0–1.7.0) plus every version-tagged commit in this repo, which leaves a real, disclosed gap at 1.3.0–1.6.x and 1.8.x, where no release notes survive in either source. It also added dashboard filter quick-toggles: a Filters section on Home showing up to five filters as name plus an enabled switch, with the drag handle, duplicate button, and selection mode staying exclusive to the full Filters screen.

Release 1.14.2 was a read-only audit of the whole app (data, messaging/service, email/Gmail, and UI layers) that produced exactly two code changes: the custom-color dialog's 512×512 hue/saturation wheel bitmap had been built synchronously inside a `remember{}` during composition — real `Canvas` work on the UI thread at the instant the dialog opens, right as its own open animation runs — and now computes on `Dispatchers.Default`; and two debug-only failure-injection preference writes used the blocking `commit()` where `apply()` was already sufficient (lint had flagged this as `ApplySharedPref`).

Release 1.14.1 fixed accent selection resetting the Settings screen's scroll position — a direct consequence of how 1.14.0 was built. That fix wrapped content in an `if`/`else` at the `SidekickTheme` call site, and each branch is a distinct composition group, so toggling Rainbow Road on or off made Compose treat the content as having moved to a structurally different parent and discard its entire subtree, wiping every `remember`ed value inside it — concretely, Settings' `rememberScrollState()`. There is now a single unconditional call site where only the *value* of a modifier on an always-present `Box` changes, which updates the node in place and never disturbs its children's identity.

Release 1.14.0 rebuilt the Rainbow Road accent as a draw-phase render effect, which is what finally fixed it rather than managing it. Every earlier attempt (1.13.4–1.13.7) treated the symptom: continuously changing `colorScheme.primary`/`secondary`/`tertiary` forces every composable reading one of those roles to recompose, and that composition-time work competes with a scrolling list's own per-frame composing and measuring. On API 31+ the accent is now a single luma-preserving hue-rotation `ColorFilter` in a `Modifier.graphicsLayer { renderEffect = ... }` wrapping the composed frame, with the hue read *inside* that block so it reruns on the RenderThread as part of the layer's draw step and never touches composition or layout — so there is nothing left to throttle or pause, and it runs at full refresh rate. Below API 31 the older throttling and scroll-pausing path is kept, not removed, since it is still load-bearing there. One disclosed tradeoff: the effect wraps the whole frame, so `colorScheme.error` (delete buttons, validation errors — never part of the accent) rotates along with everything else on this path, where it previously stayed a stable red.

Releases 1.13.4 through 1.13.7 were the four-step chase that preceded that rebuild, kept here because the reasoning is the useful part. The hue had been written on every display frame in a `withFrameNanos` loop, dropping the app to roughly 15fps; 1.13.4 throttled it to ~12Hz, 1.13.5 cut it to 5Hz after the remaining jank turned out to be specific to scrolling (a scrolling frame's budget is far tighter than an idle one, so a hue tick landing on the same frame tips it over), and 1.13.6 stopped chasing the rate and froze the animation outright during active scrolling via a shared `scrollInProgress` flag. 1.13.7 then covered the three scrollable regions that fix had missed — Home's and Developer tools' `LazyColumn`s and Settings' plain `Modifier.verticalScroll`, a different primitive needing its own overload — which is almost certainly why 1.13.6 had seemed to change nothing: Home and Settings are the two screens most likely to be the one actually being scrolled.

Release 1.13.3 fixed RCS reply routing for contacts not saved on the phone. A sender name Google Messages displays with a leading `~` means the name came from the sender's RCS profile or carrier caller-ID rather than the user's own Contacts; left in place, that character made `ContactResolver`'s exact-name lookup keep failing even after the user saved a matching contact, since nobody types `~` into a contact's name.

Release 1.13.2 addressed a battery-drain report: the foreground service's queue-drain loop posted a fresh foreground notification via `NotificationManager.notify()` (a binder call to `system_server`) on every single 5-second tick, all day, even on the overwhelming majority of ticks where nothing about the notification's text had actually changed -- a classic never-lets-the-device-sleep pattern for an always-on background service. It now only posts when the state/queued-count/Gmail-availability actually changed since the last post, and the tick interval itself was doubled from 5s to 10s (halving how often the loop wakes the CPU at all), at the cost of at most a few extra seconds of latency before a freshly queued item is picked up -- negligible next to the network round-trip an actual send already takes. Not yet measured against real on-device battery stats. The 90s Gmail reply poll, 10-minute bounce check, and (opt-in beta) 12s push pull are each their own separate network-call cadence and were deliberately left unchanged here -- shortening any of those trades battery for responsiveness and is a call worth making deliberately, not as a side effect of this fix.

Release 1.13.1 fixed a real-world incoming-MMS bug: on a slow or weak connection, the default SMS app's own download of the photo/video routinely took longer than `IncomingMessageReceiver`'s bounded wait for it, so the forwarded email arrived with only a text-only fallback notice (surfacing as something like "image" in the message) instead of the actual attachment, even with MMS forwarding enabled on the matching filter. The wait itself was never the reason it had to be short — that was `goAsync()`'s own broadcast-ANR budget — so the receiver now finishes its broadcast pending result immediately and continues the wait on the already-running foreground service instead, which let the bounded wait grow from ~3 seconds to ~28 seconds without any new ANR risk. See [Important Android MMS boundary](DESIGN_NOTES.md#important-android-mms-boundary).

The History screen's export card and event feed were also merged into a single scrollable list; previously the export card alone consumed nearly the whole screen, leaving only one or two event rows visible in a separate, barely-scrollable strip underneath it.

Release 1.9.1 fixed a duplicate-reply bug found the same night a physical device confirmed 1.9.0's MMS fix: a single email reply produced four outbound texts. `send_queue` now carries a content-based fingerprint (target number + body) so a second reply with identical content is suppressed within the same duplicate window already used for incoming messages, even if it arrives under a different Gmail message id than the first (see QA_AUDIT.md's addendum for the full finding and its open question about root cause). Release 1.9.0 closed the incoming-MMS media gap: see [Important Android MMS boundary](DESIGN_NOTES.md#important-android-mms-boundary) for the narrowly-scoped, Product-approved exception that made it possible — confirmed working against a real carrier on a physical device the same night. It also fixed a duplicate-reply bug found during that same device test (a single email reply produced four outbound texts): `send_queue` now carries a content-based fingerprint (target number + body) so a second reply with identical content is suppressed within the same duplicate window already used for incoming messages, even if it arrives under a different Gmail message id than the first. It also added two new diagnostics accessible from the home screen — **Send Test Message**, which runs a synthetic message through your real filter configuration and reports which filter (if any) matched, and **Test Gmail Connectivity**, which sends one email directly to your connected Gmail account, bypassing filters entirely, to isolate a broken OAuth/API connection from a filter-configuration problem — plus an **Export message log** action on the History screen (CSV, a chosen date/time window, message text opt-in and off by default).
