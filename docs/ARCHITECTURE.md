# Architecture

## Live receive path

`IncomingMessageReceiver` is registered in the manifest and dynamically by `ForwardingService`. Duplicate delivery is expected and safely collapsed by Room's unique `(senderAddress, sourceTimestampMs, bodyHash)` index. Broadcast receipt time—not the SMS service-center timestamp—is used for the strict forwarding-watermark decision.

The receiver calls `goAsync()`, parses only the current intent, and passes an `IncomingMessage` to `SidekickRepository.processIncoming`. The repository performs these actions in one database transaction:

1. log receipt;
2. read the single forwarding state row;
3. reject OFF or `receivedAt <= watermark` events;
4. insert the dedupe/audit row;
5. insert one persistent email queue row; and
6. log the enqueue.

There is intentionally no Telephony content-provider observer, cursor, catch-up worker, or last-seen message ID. The one narrow exception (release 1.9.0, Product-approved) is `MmsContentFetcher`, invoked only from `IncomingMessageReceiver`'s `WAP_PUSH_RECEIVED` handling: a single bounded, event-triggered read of the one `content://mms` row that specific broadcast just announced, never a range or a persisted bookmark. See README "Important Android MMS boundary" and `scripts/verify_no_history_queries.sh`, which enforces that this is the only file allowed to touch the SMS/MMS content provider at all.

`RcsNotificationListenerService` handles the Android gap for RCS, which has no third-party receive broadcast. It accepts only newly posted conversation notifications from Google Messages and Samsung Messages, ignores group-summary notifications, extracts the newest messaging-style entry, and sends it through the same repository transaction. It never calls `getActiveNotifications()` or reads message history. Because those apps also notify for SMS, notification intake waits briefly and the repository compares it with its own recent live SMS/MMS records before enqueueing. The notification path is best effort: Android may omit muted, blocked, hidden, or media content.

## Delivery path

`ForwardingService` runs two independently limited channels:

- `EMAIL`: 20 rolling minute / 300 rolling hour / 450 rolling 24 hours. Ordinary forwards stop at 20 / 290 / 420 so receipts, status replies and the heartbeat keep a reserve; attempts are counted together, so the total never exceeds the first set.
- `SMS`: 10 rolling minute / 60 rolling hour / 200 rolling 24 hours (shared with MMS).

`QueueProcessor` claims one Room row, asks `RollingRateLimiter` for the earliest safe time, and reserves a `delivery_attempts` record before calling an external API. A process death can therefore under-send but cannot allow a rate-limit reservation to disappear.

Email sends carry a deterministic RFC `Message-ID` derived from immutable queue data. An interrupted email claim is delayed, then Gmail Sent mail is searched for that ID before retrying; a match records success without sending a duplicate. Neither SMS nor MMS can be reconciled without reading provider history, so an interrupted `SENDING` row on either channel is moved to `DEAD` and surfaced for review (`QueueDao.quarantineInterruptedTelephonyClaims`). This deliberately prefers a possible missed reply over an unsafe duplicate.

Email failures increment the singleton consecutive-failure count transactionally. Success resets it. Failure five opens `emailCircuitOpen`, halts the email channel, and posts an ongoing high-priority notification. Queue rows remain durable until the user manually resets the breaker.

## Gmail reply path

Every 30 seconds, the foreground loop uses Google Identity Services to obtain a fresh access token without UI when a grant is still valid. It asks Gmail's history log whether the inbox changed since the last poll and, if so (or on a periodic full sweep), lists recent inbox messages whose subject contains `SCIF` or `TEXT`. For each candidate it fetches only the routing and authentication headers, and applies the exact routing regex `\[SCIF:(\+[1-9]\d{6,14})]` to the decoded Subject header. The body and any image are fetched only after the sender is authorized.

The subject tag alone is not authority to send. `sent_email_routes` records the Gmail thread ID and RFC Message-ID for every forward. A reply must match that route and the same target number through its Gmail thread or `References`/`In-Reply-To`; otherwise it is recorded as a security event and marked read without sending.

`processed_replies` and the SMS or MMS `send_queue` insert occur in the same transaction, preventing a Gmail polling duplicate (the same Gmail message id seen again) from generating two sends. That alone does not catch two genuinely distinct Gmail messages that carry the same target number and body -- observed in practice from what looked like a mail client silently resubmitting one reply. `send_queue.replyDedupeKey` (release 1.9.1, `SidekickRepository.enqueueReplyIfNew`/`enqueueMmsReplyIfNew`) closes that gap: a SHA-256 of `targetNumber|normalizedBody`, checked against every SMS/MMS row queued within the same `duplicateSuppressionEnabled`/`duplicateWindowMinutes` window that already governs incoming-message dedup. The Gmail message is marked read only after the queue insert (or dedupe skip) succeeds. Individual malformed/failing message fetches are isolated so one bad message cannot prevent other replies from being processed.

## Mail transports

All mail goes through the `MailTransport` interface (`graph.mail`); the forwarding, reply and send-queue code never touches a provider API, except Gmail push, which `ForwardingService` and `GmailWatchRenewalWorker` call through `graph.gmailPush`. `GmailGateway` is the only implementation, and no other provider is supported.

Everything provider-specific lives in the Gmail adapter (`email/`): the search syntax for remote commands (`GmailCommandQuery`, built from a neutral `CommandSearch`), sender authentication (`GmailAuthentication`, which turns Gmail's `Authentication-Results` headers into the neutral `authenticatedFromAddress`), OAuth and token storage (`GmailOAuthManager`), and Pub/Sub push (`GmailPushGateway`, reached through `graph.gmailPush`). The connect, disconnect and push settings in `MainViewModel` still use `graph.gmail` and `graph.oauth` directly by design.

Message ids are scoped by provider with `MailIds`. Gmail ids stay unprefixed exactly as already stored, so no migration was needed. Any other provider's ids are `<providerId>:<id>`, split on the first colon only, so ids from two providers can never collide in `processed_replies` or in routing.

`MailAuthRequiredException` is the one shared "reconnect needed" error. Callers pause work and alert on it without knowing which provider raised it.

A new transport must pass `MailTransportContract` (in `src/test`), by subclassing the contract and supplying its own harness implementing `MailTransportContract.Harness` (it can sign out and deliver a message). `FakeMailTransport` (`src/sharedTest`, used by both unit and instrumented tests) is the reference implementation.

## Tables

- `forwarding_state`: enabled, watermark, destination, breaker state, consecutive failures, MMS-forwarding toggle, call-notification toggle, contact filter mode and number list.
- `forwarded_messages`: live-message dedupe and forwarding audit.
- `send_queue`: durable email, SMS-reply, and MMS-reply (picture message) work, keyed by `channel` (`EMAIL`/`SMS`/`MMS`).
- `delivery_attempts`: rolling-limit reservations and outcomes.
- `processed_replies`: Gmail reply idempotency.
- `sent_email_routes`: authorization link from an app-sent Gmail message/thread to one E.164 target.
- `event_log`: user-visible structured diagnostics.
- `forwarding_filters` (added in version 5): one row per named forwarding rule — message types, recipients, conditions, template, schedule, save/notify toggles.
- `app_settings` (added in version 5): the singleton row for app lock, font scale, duplicate-suppression window, soft anti-flood ceilings, retry-on-reconnect, and compose-new-via-email.

Database version 2 adds `sent_email_routes` through an explicit 1→2 migration. Version 3 adds the four `forwarding_state` columns above through an explicit 2→3 migration (`ALTER TABLE ... ADD COLUMN`, each with a default matching the pre-migration behavior). Version 5 adds `forwarding_filters`, `app_settings`, and a `dedupeText` column on `forwarded_messages` (used only for the cross-source duplicate comparison, never for what actually gets forwarded), and seeds one filter from whatever `forwarding_state`'s now-frozen destination/MMS/call/contact-filter columns held. Version 6 adds `forwarding_filters.stopOnMatch`. Version 7 adds `app_settings.authorizedComposeSendersJson` (the compose-new-via-email allowlist, defaulting to `[]`) and, for installs upgrading from before 1.4.0's `duplicateWindowMinutes = 60` default, resets that column to the new `1`-minute default. Version 9 adds `send_queue.replyDedupeKey` (nullable, indexed with `channel` and `createdAtMs`) for reply-send duplicate suppression. Completed payloads are retained for 30 days; reply routes, processed-reply IDs, and events are retained for 90 days. Pending and dead-letter work is not automatically deleted.

Versions 10 through 18 (each covered by a `Migration*InstrumentedTest`): 10 adds heartbeat, snooze, and retention defaults; 11 adds Gmail push defaults; 12 adds remote-enable defaults; 13 adds remote-disable defaults; 14 turns reply confirmations on for upgrading installs; 15 adds heartbeat defaults across both state tables; 16 adds status-command defaults without inheriting other commands' authorizations; 17 leaves outbound SIM on the system default; 18 consolidates the four remote-control allowlists into one (`remoteControlEnabled` / `remoteControlSendersJson`). The authoritative schema for every version is in `app/schemas/`.

## Forwarding gates (`SidekickRepository.processIncoming`), release 1.4.0

An incoming message is recorded and deduplicated exactly once (watermark, same-source duplicate-notification suppression, then cross-source dedupe, then the unique-insert constraint), all still ahead of any per-filter logic and all still enforced regardless of how many filters exist. `processIncoming` then loads every `enabled = true` row from `forwarding_filters` and, for each, evaluates in order: message-type scope (`includeSms`/`includeMms`/`includeRcs`/`includeCalls`), its schedule window if one is set (`ScheduleWindow`, handling an overnight window), and its forward-by-conditions check if `conditionMode = CONDITIONS` (contact allow/block list against the sender normalized to E.164, and/or a keyword must-contain/must-not-contain check) — unless `OtpDetector.looksLikeOtp` and the filter's `alwaysAllowOtp` is set, which bypasses only the contact/keyword conditions, never the message-type or schedule gates. A filter that passes renders its own subject/body template (`MessageTemplateEngine`, `MessageVariables`) plus find-and-replace rules (`ReplaceRuleEngine`) and queues its own `send_queue` row addressed to its own recipients; one message can fan out to zero, one, or several filters. A blocked or non-matching filter is a hard skip, logged and never reaching `send_queue`, identical in effect to the master `enabled == false`. `IncomingMessageReceiver` additionally peeks whether *any* enabled filter currently wants MMS (`FilterDao.anyEnabledWantsMms`) before copying any attachment bytes to disk, so a disabled attachment never touches app storage even transiently when nothing would use it; the transactional per-filter check inside `processIncoming` remains the sole authority. Because more than one filter's queue row can reference the same copied attachment file, `QueueProcessor` only deletes an attachment after send once no other still-active row references it (`QueueDao.activeAttachmentPathJsons`).

Missed calls are sourced from `RcsNotificationListenerService`, which also listens for the device's default dialer package (resolved via `TelecomManager.getDefaultDialerPackage()`, with a small known-package fallback) and reads the standard `Notification.CATEGORY_MISSED_CALL` category — never the call log. A detected missed call is turned into the same `IncomingMessage`/`processIncoming` pipeline as SMS/MMS/RCS, under `source = "call"`, which is why it is also subject to each filter's conditions and produces a normal reply-routable forwarded email.

`forwarding_state` keeps owning only what is genuinely global and safety-critical: the master enabled switch, the watermark, and the email circuit breaker. Its pre-1.4.0 destination/MMS-toggle/call-toggle/contact-filter columns are left in place, frozen and unread by the app from here on, having been used only by the 4→5 migration to seed one filter for upgrading installs. `app_settings` is a second global singleton row for app lock, font scale, duplicate-suppression window, the two soft anti-flood ceilings, retry-on-reconnect, and compose-new-via-email.

Composing a new outbound text from a freshly written email (rather than replying to one) has no prior sent thread to authorize against, so `ForwardingService.pollReplies` instead requires the feature to be enabled and the email's `From` address to appear on the remote-control allowlist (`app_settings.remoteControlSendersJson`, one list for all four email commands, each address carrying its own per-command checkbox; consolidated in release 1.23.0, schema version 18, from the earlier per-command lists such as `authorizedComposeSendersJson`, which are kept in place but no longer read). `ComposeAuthorization.isAuthorizedSender` (added release 1.7.0 in place of the earlier "must match the connected Gmail account's own address" rule) still performs the check; anything not authorized is recorded as a `SECURITY` event, exactly like a forged `[SCIF:+number]` reply tag. The master switch `remoteControlEnabled` defaults to on, and the allowlist column defaults to `[]`, but the connected Gmail account is added automatically the first time (`seedRemoteControlOwnerIfEmpty`) with all four commands checked (releases before 1.26.0 checked only Status, and installs that already seeded keep that), so any other address authorizes nothing until you add it. The trigger subject itself is just `TEXT+<E.164 number>` (`PhoneNumbers.extractComposeTarget`, word-boundary-anchored so it can't match inside another word) — no bracket/colon syntax, unlike the `[SCIF:+number]` reply tag.

An image attached to an authorized trigger (reply or compose-new) is sent as an MMS instead of an SMS. `GmailGateway.fetchMessage` recursively scans the message payload for the first MIME part whose type starts with "image", fetching its bytes either inline or via a separate `messages.attachments.get` call, gated by `AttachmentStore.MAX_STORED_ATTACHMENT_BYTES` both from the part's declared size and the attachment endpoint's own reported size. `ForwardingService` then stores those bytes on disk (`AttachmentStore.writeBytes`) and queues a `QueueChannel.MMS` row (`SidekickRepository.enqueueMmsReplyIfNew`) instead of the ordinary SMS one; `MmsGateway` wraps `com.klinkerapps:android-smsmms` (Android has no public high-level MMS-compose API of its own -- the PDU classes were removed from the SDK) using its "system sending" path, downscaling the image's pixel dimensions -- not JPEG quality, which the library hard-codes to 90 regardless of what it's given -- to a conservative size budget first. **MMS-out cannot be verified against real carrier/MMSC infrastructure without a physical device on a live SIM**; this is a disclosed, untested risk area, not a claim of confirmed delivery. `QueueChannel.MMS` shares the SMS channel's hard and soft rate-limit tiers (`RollingRateLimiter`, `QueueProcessor.drain`'s soft cap) rather than getting a ceiling of its own.

`pollReplies` also checks `SentEmailRouteDao.isOwnSentMessage` on every candidate message *before* looking at its subject at all. This exists because a filter's recipient can be the same connected Gmail account: the app's own outgoing notification then lands back in that inbox as a new unread message, already carrying a genuine `[SCIF:+number]` tag whose thread `sent_email_routes` recorded as authorized the moment it was sent. Without this check, that notification would satisfy `isAuthorizedReply` against its own route and get treated as a reply to itself.

Filters are evaluated in `sortOrder` (the same order `FilterDao.getEnabled()`/`getAll()` return); the Filters screen's drag-to-reorder writes a new `sortOrder` per filter via `SidekickRepository.reorderFilters` in one transaction. A filter's `stopOnMatch` flag, when it both matches and actually queues a forward, ends the per-filter loop for that message -- no filter after it in that order is evaluated, mirroring "stop processing more rules" in an email-client filter chain.
